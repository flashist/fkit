## Accepted residuals (shared, do-not-re-litigate)
- **Ranks past 2^53** — What: ranks above 9007199254740991 (from a hand-typed huge rank, or an id ≥ about 9×10^12) are held as JS numbers, so ranks worked out from them can be saved slightly wrong; `check()` reports every such rank (a deliberate addition to aiboard's `check()` output). · Why (structural): `Task.rank` in 0417's `model.mjs` returns a JS number, and 0418's approved plan leaves `model.mjs` untouched; making ranks `BigInt` end to end is a cross-task change. Owner ruling 2026-10-21, `AskUserQuestion`, `fkit lead` session: first *"Accept as known gap (Recommended)"*, then, re-asked after the loss was found silent at 2^53+1, *"Make it loud (Recommended)"* (description: *"0418's health check flags ranks too big to store exactly; the gap itself is accepted as known."*). Rejected: fixing `model.mjs` here (outside the plan); leaving it silent (owner ruled against). · Re-raise only if: a real board (fkit's corpus or a user's) holds a rank or id past 2^53, or a later task changes `Task.rank` / the store's rank arithmetic. *(Clarified 2026-10-21, review round 3, wording only: "above 9007199254740991" and "past 2^53" mean outside -9007199254740991..9007199254740991. A rank below -9007199254740991 loses precision the same way, comes from the same cause, and is reported by the same `check()` message (R6). The ruling's scope is unchanged.)*
- **Terminated worker thread holding the lock** — What: a worker thread ended with `worker.terminate()` while it holds the board lock leaves `.aiboard.lock.owner`; same pid, other `threadId` reads as alive, so every writer in every process waits, silently, until that whole process exits. A worker that throws or returns releases normally. · Why (structural): a terminated worker runs no `exit` hook (probed 2026-10-21), and Node has no API that tells one thread whether another `threadId` still runs; breaking same-pid other-thread records on a timeout would break live holders, which the ruling forbids. Owner ruling 2026-10-21, `AskUserQuestion`, `fkit lead` session: *"Fix cheap ones, list rest (Recommended)"* (description: *"Coder fixes what it reasonably can; the rest go in the lock's limits list + a note for 0422."*). Worklog locking limit 13; 0422 must never terminate a worker that may hold the board lock. · Re-raise only if: fkit code (0422's server or later) runs board writes in worker threads that can be terminated, or Node gains a cross-thread liveness API.
- **Unreaped (zombie) lock holder** — What: a holder that was killed but not yet reaped passes `kill(pid, 0)` and reads as alive; a process that kills its own holding child and then writes before its event loop reaps it waits forever, silently. · Why (structural): no cross-platform zombie check exists without spawning `ps` in the wait loop; Linux `/proc` would cover one platform only and cannot be tested on this machine. Same owner ruling as above (*"Fix cheap ones, list rest (Recommended)"*). Worklog locking limit 14; 0422 must wait for `close`/`exit` of any child it kills before its next board write. · Re-raise only if: fkit code kills a child that may hold the board lock and writes before reaping it, or a hang of this kind is seen.
- **Hostname change after a holder died** — What: if `os.hostname()` changes (macOS does this when the network changes) while a dead holder's owner file is on disk, the record reads as "another host" and every writer waits forever, silently, until someone deletes `.aiboard.lock.owner`. · Why (structural): the host check stops a writer judging a remote holder dead from a local pid check; treating other-host records as breakable would break live holders on shared volumes. Same owner ruling as above (*"Fix cheap ones, list rest (Recommended)"*). Worklog locking limit 15. Reasoned, not measured. · Re-raise only if: the hang is seen in use, or the lock gains a host identity that survives a hostname change.
