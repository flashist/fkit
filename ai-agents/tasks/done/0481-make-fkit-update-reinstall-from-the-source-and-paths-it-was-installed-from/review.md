| R1 | 1 | low | install.sh:68 | `BIN="$(cd "$BIN" && pwd)"` is not safe when `CDPATH` is exported. With a relative `FKIT_BIN` that matches a `CDPATH` entry, `cd` goes to the CDPATH directory, not `./$BIN`, and also prints that path, so `BIN` becomes two lines. Measured under dash and under /bin/sh: `[<cdp>/bin\n<cdp>/bin]`. The wrapper and `bin=` then land in the wrong place, which is the thing the brief forbids. This line was added by 0481; before it, a relative BIN was used as given and `CDPATH` had no effect. Raised by both reviewers (Codex X1). Fix direction: `CDPATH= cd -- "$BIN"`, or unset `CDPATH` near the top of the script. |
| R2 | 1 | medium | claude/fkit-claude.sh:137 | `fkit_share="${FKIT_SHARE:-$share}"` trusts `$share` (`$here/..`, where `here` comes from `dirname "$0"`) without checking that it is a real install. If the launcher is reached through a symlink or a copy (for example `~/bin/fkit -> …/share/fkit/claude/fkit-claude.sh`) and `FKIT_BIN` is set, the installer is handed `FKIT_SHARE=<parent of the symlink's dir>`. Measured under dash: the capture showed `SHARE=<probe>`, the symlink's parent. The real `install.sh` then runs `rm -rf "$SHARE/claude"` and `rm -rf "$SHARE/omnigent"` and writes `.version` there, for example in `~` for a symlink in `~/bin`. Before 0481 the same run went to the default share. Without `FKIT_BIN` it refuses safely, but only by luck: `.version` is missing there. The setup is unsupported and unlikely, but the result is destructive. Fix direction: refuse unless `$share` looks like an install (e.g. `[ -f "$share/.version" ]` or `[ -f "$share/claude/fkit-claude.sh" ]` holding this script), or resolve `$0` through symlinks. Add a test case. |
