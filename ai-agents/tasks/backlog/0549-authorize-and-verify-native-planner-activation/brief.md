## Context

Unit C of the accepted [0546 specification](../../../knowledge-base/reports/2026-11-12-design-native-fkit-planner.md),
§§11–12, is **separately consent-gated activation and verification**, after
[0548](../0548-build-planner-all-native-planning-paths-and-exact-record-handoff/brief.md).
[ADR-062](../../../knowledge-base/decisions/adr-062-native-opencode-only-branch-and-native-source-authority.md)
and [ADR-063](../../../knowledge-base/decisions/adr-063-planner-owns-native-task-planning-and-post-decision-records.md)
are accepted policy/design, not evidence of implemented or activated behavior.
Owner acceptance **"Accept design (Recommended)"**, primary OpenCode `fkit-lead`, question channel,
2026-11-12, relayed by lead, authorized records/briefs only. Full four answers:
[0546](../0546-design-fkit-planner-and-task-planning-ownership-transfer/brief.md), *Context*.

**Do not execute this brief merely because it exists or its dependency is built.** Coder owns the
bounded technical activation/check assignment and evidence; live primary holds all consent and
spawns only actual available roles. Before any refresh/generation/install/update/native CLI/live
fixture, present exact targets, commands, expected writes, preservation safeguards, model/cost
impact and checks to the owner, and obtain actual explicit authorization. Test execution is paused
by the 2026-11-11 ruling and needs an explicit test request; design, build or generic verification
approval is not that request. No standalone Claude/Codex orchestration bridge or stopped Claude
check is authorized. Before activation, use current callable roles, not a fictitious planner.

## What to build

1. Prepare a bounded activation/verification plan from actual `0547`/`0548` delivered source and
   open verification gaps. Separate read-only inspection, generated/installed writes, live native
   role calls and test execution. Name target checkout/install/fixture, exact approved action list,
   expected generated outputs, preservation/rollback needs and required owner interactions. Return
   `NEEDS-DECISION` to primary for missing consent; do nothing while awaiting an actual answer.
2. Only within the owner's enumerated authorization, activate/register canonical native outputs
   and inspect installed discovery, command/skill ownership, artifact permissions, leaf/depth
   policy, team-versus-hostile model inheritance and native entry/install/update/resource behavior.
   Preserve user knowledge/config/preferences/authentication/ignore rules and prior manifest hashes.
   No broad permission changes, legacy deletion, source fixes or configuration/model resets are
   implicitly permitted. New changes outside the approved activation scope return to the owner.
3. Once genuinely available, verify the new native routes with owner-approved disposable fixtures
   and actual named roles: lead conductor/sprint planning, coder primary/task loop, plain planning,
   planner primary, inline and non-source planning. Confirm primary-owned question relay and
   approval, read-only Draft/review, separate planner Record, original-byte/full-review/actual-answer
   validation before correct producing-role Build. A planner-primary packet needs adoption by a
   new source-driving primary; plan-only intent must not start Build. Never trigger real source
   writing, ledger mutation or lifecycle actions as an unapproved probe side effect.
4. Exercise only explicitly authorized exact-record/failure cases: UTF-8 fidelity, expected-hash
   and symlink checks, identical/conflicting retries, rejection with older plan, torn two-file state,
   revision, wrong/new primary and lost inline store. Verify inline ignored storage creates no
   tasks; task records retain correct ownership. Observe actual outcomes rather than inventing
   tool results or calling a documented plan a completed check.
5. Check all-path review ON/default and explicit opt-out origin/reporting, classification approvers,
   round cap, independent reviewer → hostile depth-three chain, no ancestor cycles and read-only
   wiki lookup. Actual runtime model evidence is required for diversity; same/unknown/missing/
   unusable output remains prominently partial. Reasoning-only is not test execution. No automatic
   closure with partial review or incomplete required checks.
6. Record a secret-safe verification report: exact authorized actions and provenance, actual role
   availability, targets/versions, observed outputs, hashes/byte counts where relevant, failures,
   skipped/unrun checks and remaining risks. Distinguish policy accepted, source implemented,
   generated/discovered, installed and live verified. Report permission/quota/owner-interaction gaps
   plainly; never refresh permissions to bypass a denial or silently broaden consent. Source
   defects return for separately approved coder work, not hidden fixes in this verification task.

## Verification steps

1. Each executed activation/live action maps to explicit owner authorization quoted with date,
   channel and exact scope; each test run maps to an explicit test request. Missing consent leaves
   that action unrun, never passed. Stopped Claude checks remain stopped.
2. Report actual new-role discovery and permitted/denied capabilities, effective command/skill
   registration, retained compatibility resources, model/config preservation and entry behavior.
   The source role definition alone is not a callable-role or shipping-verification claim.
3. Authorized entry/failure/review matrices have observed outcomes with evidence or a specific
   unverified reason for each case. No hashes-as-consent, OS-sandbox, transaction or model-diversity
   claims exceed the evidence. Negative cases withhold Build instead of granting a fallback.
4. Check authorized write surface and preservation against before/after evidence; no source repair,
   old task/sprint record edit, vault write, legacy deletion or unrequested model change slipped in.
   Restore disposable fixtures only within approved cleanup scope; do not delete owner artifacts.
5. Independent review and completion report list remaining verification/permission/consent gaps.
   This task performs no lifecycle closure; producer mover and agent-closed-marker rules remain.
